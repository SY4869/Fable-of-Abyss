Ⅱこのサイトを作った理由

最初のきっかけは単純で、『フェイブル・オブ・アビス』を自分以外の人にも遊んでほしかったからです。作ったものが自分の手元にしかないのでは、完成させた意味が半分になってしまいます。

公開の方法は、はじめ AWS Lightsail を使うつもりでした。ところが調べていくうちに、GitHub Pages ならもっと低い費用で公開できると分かり、そちらへ切り替えました。いまもその形のまま動いています。

ドメインは、せっかく公開するならちゃんとしたものにしたいと思い、sygames.net を取得しました。

Ⅲこのサイトの目的

二つあります。

  • 自作ゲームを公開して、無料で誰でも遊べる場所にすること。インストールもアカウント登録も要らず、開いたその場で始められること。
  • ゲーム制作で学んだ知識や技術を記録する場にすること。作って終わりにせず、何を考えてそうしたのかを残しておくこと。

二つ目のために制作記録を置いています。うまくいった話だけでなく、途中で壊した仕様や、いまも直しきれていないところも書いています。

Ⅳゲームを作っている理由

もともと YouTube での動画投稿や、TRPG のシナリオ作成などを趣味でやっていました。ゲーム制作もその一つで、たまに手を出してはいました。

ただ、ゲームはほかの趣味と比べて完成させる難易度が高いものでした。動画もシナリオも、ひととおり終わらせれば形になります。ゲームはそうはいかず、途中で辞めることのほうが多かったのが実情です。

最近になって AI の性能が上がり、このハードルが大きく下がりました。結果として、初めて完成まで辿り着けました。かけた時間や労力を振り返ってみて、今後も作っていけそうだと感じています。

Ⅴどんなゲームを作りたいか

個人制作なので、できることには限りがあります。2D で、低予算でできるものが前提です。そのうえで、基本的には短時間で遊べるゲームを作りたいと考えています。

大切にしているのは、自分が楽しめるゲームであることです。そのために、公開する前にまず自分でクリアするまでテストプレイをします。自分で最後まで遊べないものを人に出すことはしません。

この方針から、公開しているゲームには共通する作りがあります。

  • ブラウザだけで完結すること　何かを入手させたり、アカウントを作らせたりしない。
  • 短く終われること　やりこみ要素はあっても、一回ぶんは隙間時間に収まる長さにする。
  • 腕前が理由で結末に届かない作りにしないこと　難しさは選べるようにする。

Ⅵ使っている技術

プログラムCODINGClaude Code でのバイブコーディング。プログラム自体は、ほとんど Claude Code が担当しています。
指示の作成PROMPTGemini や GPT を使って、指示の文面を整えています。
基本FRONTHTML / CSS / JavaScript。ゲーム本体もこの三つだけで書いています。
サーバー側BACKEND必要になるものには Python を使う予定です。現在はカオスソードガーデンのランキングにサーバーを使っています。
公開HOSTINGGitHub Pages。独自ドメイン sygames.net を割り当てています。
この先FUTURE将来的には Steam などでも公開したいと考えています。

ゲーム本体は素の JavaScript だけで書いています。ゲームエンジンも、描画ライブラリも、ビルドツールも使っていません。『フェイブル・オブ・アビス』は描画に Canvas 2D、音に Web Audio API を使い、480×640 の画面を 60fps の固定タイムステップで動かしています。

ライブラリを避けているのは主義の問題ではなく、単に読み込みを速くしたかったからです。ページを開いてから遊び始めるまでに待ち時間があると、それだけで人は帰ってしまいます。フレームワークを一つ入れるとその分だけ起動が遅れるので、必要なものを自分で書くほうが目的に合っていました。

最初の版は、画像も音楽もすべて Base64 で HTML に直接書き込んだ一枚の巨大なファイルでした。どこにでも置けて確実に動く反面、18MB という極端な大きさになり、開くたびに全曲を読み込む形になってしまいます。現在は素材をファイルへ切り出し、必要になった時点で取りに行くよう作り直しました。

技術的に苦労したこと

  • AI に任せきれない部分が多かったこと　書いてもらうこと自体はできても、仕様を正確に伝えるのは別の作業でした。詳しくは制作記録に書いています。
  • 難易度調整　作った本人は中身を全部知っているので、初見の難しさが測れません。
  • Web への公開　作ることと、人が開ける場所に置くことは別の作業でした。
  • ドメインの取得
  • 広告配信サービスへの申請

Ⅶ動作の確認について

弾幕を1つ調整すると、一見関係のない場所の難易度が変わることがあります。そのため、ゲームを自動で動かして仕組みを検査するテストを 78 項目書き、リリース前に通すようにしていました。技名が正しいか、難易度の係数が実際の弾に効いているか、ボムが五種類とも仕様どおり働くか、といった項目です。

さらに、わざと壊した版を作ってテストが赤くなるかも確かめました。これは有効で、実際に「盾を無効にしてもテストが通ってしまう」抜けが見つかっています。自機の弾は別の場所で止まっていたため、ボムだけが盾を貫通する状態を見逃していました。

ただし自動化できるのはここまでです。実際の見た目、音の自然さ、そして「その弾幕が理不尽かどうか」は数値で測れないので、最後は自分で遊んで判断しています。
